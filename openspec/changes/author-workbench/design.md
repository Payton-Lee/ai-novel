## Context

动机见 `proposal.md`。代码观察：

- `web/src/app/page.tsx` 主要挂载聊天 Thread；尚未在该入口形成章节编辑工作台。
- `src/director/tools.py` 的 `prepare_serial` 未接收已生成的完整大纲，通过 `_generate_outlines(idea, genre, n)` 重新生成，并返回手动启动说明。
- `setting_studio/project_store.py` 与 `serial_engine/storage.py` 使用不同身份和存储；后者的 `save_chapter` 使用覆盖写入。
- `serial_engine` 已具备分层记忆、任务单、角色认知与局部重写基础，应复用。
- 前端已有 Playwright 依赖但未配置测试脚本；后端已有测试主要是模板烟测。

上述为静态检查结果，尚无运行基线；首个阶段必须记录环境、失败项和现有样例行为。默认单作者本地使用，模型保持可配置。

## Goals / Non-Goals

**Goals:** 建立统一数据归属、可追溯输入快照、可靠写入和可恢复任务；以渐进方式复用 LangGraph。

**Non-Goals:** 首版不引入多人权限体系、云端调度集群、向量数据库替换或自动发布。不会把“支持很多章”的存储能力当作长期叙事质量已验证。

## Decisions

### 1. 应用服务统一读写

新增 Python 书籍应用服务（建议 `src/book_workspace/`）作为权威写入入口，提供书籍、设定、大纲、章节、版本与任务 API。通过独立本地 ASGI 服务承载，Next.js 显式代理 `/api/books`，现有 catch-all LangGraph 代理保持用于会话。服务仅绑定回环地址；浏览器不得接触模型密钥。

选择理由：在 Python 侧复用现有存储和工作流，避免 Next.js 与 Python 分别操作 SQLite。替代方案为将路由挂入 LangGraph 服务，但会加深对运行平台接口的依赖；本轮采用独立服务，并提供统一启动脚本降低使用成本。新增依赖和端口集中配置，补充打包声明。

### 2. 统一身份，逐步迁移

新增稳定 `book_id`，记录旧 `project_id`、`story_id` 与源数据库位置的映射；不凭书名推测合并。新应用数据库增加 book、setting_revision、outline_revision、chapter_revision、generation_run、memory_snapshot、consistency_issue 和迁移记录。

既有数据库先只读导入到新库，保留原文件；兼容适配器将旧工作流读写引向新服务，避免长期双写。每章保存使用单事务更新版本与当前指针。备份必须使用一致性快照，不能在写入期间只复制主数据库文件。

替代方案为立即合并所有旧表并删除原库，迁移风险过高；仅增加名称映射而维持多套权威数据则不能解决漂移。

### 3. 确认和生成使用版本快照

确认大纲后保存结构化分卷与章节；旧文本大纲先解析为草案，作者确认后生效。导演调用应用服务创建任务，传入大纲、设定和风格版本；不重新生成已确认大纲。每次运行保存输入版本与提示词版本，正文结果先作为候选版本展示。

锁定设定只能由作者明确解锁或接受修改提案来改变。采用正文后才更新供后续写作使用的记忆；后台生成草稿不污染当前有效事实。自动连写模式由作者明确选择自动采用策略，并保留每章版本。

### 4. 编辑器先交付可靠文字操作

采用现有 React 组件先实现纯文本章节编辑器、目录和侧栏，提供自动保存状态、手动保存及选区修改；富文本排版留待后续需求。请求携带基准 revision，冲突返回可比较结果；局部建议绑定章节版本和选区内容校验，过期建议禁止直接应用。

恢复操作新增版本。原 `chapter` 可作为当前稿件投影兼容旧导出逻辑，历史以追加版本为准。导出只读选定版本，不携带会话或密钥。

### 5. 按章节边界维护记忆

记忆快照绑定正文与设定版本。首版采用保守策略：旧章修改后，从该章开始重建派生记忆并标记后续问题报告过期；不自动重写后续正文。重建完成以事务切换有效快照，失败保持过期状态。生成只读取当前章之前的事实，避免读取未来章节导致剧透。

先保守失效而非建设复杂依赖图，可降低漏更新风险；代价是重建成本较大，由任务队列显示进度。后续再根据记录优化为细粒度失效。

### 6. 持久化单工作进程任务队列

首版使用 SQLite 任务表和单工作进程，记录 queued/running/pause-requested/paused/succeeded/failed/cancelled 状态、阶段检查点、输入快照、幂等键和心跳。启动时将失去心跳的运行标记为可恢复，不能盲目重复执行已提交的章节。

暂停在模型调用之间生效。一次模型返回后先持久化结果，再事务提交阶段状态；外部模型在崩溃窗口可能重复收费，UI 说明该限制，但本地版本提交必须幂等。同一本书的写作与记忆重建串行，跨标签页也通过数据库锁和 revision 防护。

每次调用前预留 token/调用额度，完成后用实际值结算；缺失统计保留未知标记。货币估算记录模型、单价来源和时间，不在计划中硬编码当前价格。

### 7. 质量反馈可回溯

问题记录绑定章节版本和来源片段，包含确定性等级与处理状态。复用现有读者模拟和局部重写，但把追读“预测”改为编辑建议。风格配置从书籍到章节逐级覆盖并进入所有阶段，消除辅助生成器中无条件番茄提示词。

## Delivery Plan

| 阶段 | 依赖 | 交付与发布门槛 |
| --- | --- | --- |
| P0 创作闭环 | 无 | 统一书籍、最小版本保护、大纲直达正文、基本编辑和导出；完成第一章并续写第二章，无参数搬运 |
| P1 安全修改与恢复 | P0 | 完整版本比较、局部修改、持久任务、暂停和故障续写；验证双页面冲突和第四章失败恢复 |
| P2 长篇一致性与风格 | P1 | 旧章记忆重建、带出处的问题、伏笔面板和风格贯通；修改第三章后续写不能使用旧事实 |
| P3 资源控制与作者验证 | P2 | 用量预算、固定十章评测和作者试用；按记录判断是否达到候选发布条件 |

任务编号对应 `tasks.md`。按阶段提交和演示，禁止仅因 P0 完成而归档整个变更。若需要独立归档，应先用 OpenSpec 更新流程拆成子变更并同步需求，避免丢失后续工作。

## Validation Strategy

- 自动化：pytest 使用临时数据库和确定性模型替身，覆盖迁移重复执行、故障回滚、版本竞争、大纲传递和任务幂等；Playwright 覆盖创作、编辑、恢复与继续。真实模型测试单独运行并记录用量。
- P0 首先测量当前主线与 UI 基线，区分既有失败与新增回归；后续执行受影响测试及现有检查，不掩盖已有失败。
- 固定十章夹具包含人物秘密、年龄约束、三条伏笔和旧章修改；保存模型标识、参数、提示词版本、输入与输出。人工判断不得由同一次生成模型的自评分替代。
- 硬门槛：无手动搬运参数；已完成稿件不丢失；恢复内容完全一致；重复启动不重复提交；故意植入的确定性事实冲突必须识别，错误报告需可追溯。
- 体验目标：邀请至少三位目标作者各完成两章，至少两位独立完成闭环；记录首章耗时、人工改稿分钟数和建议采纳情况。耗时相对基线下降为优化目标，不伪造尚未获得的收益；未招募到作者则 P3 保持待验收。

## Risks / Trade-offs

- 模型输出结构不稳定 → 结构校验失败保留原文和重试入口，禁止悄悄生成替代大纲。
- 迁移误关联或新旧双写 → 显式映射、只读预演、幂等导入与切换后单一写入入口。
- 记忆重建成本高 → 可恢复队列和保守失效；预算不足暂停，不用旧事实凑合继续。
- 额外本地服务增加启动负担 → 统一启动与健康检查，错误以中文说明。
- 范围跨越多个模块 → 四阶段分别验证，先交付最小闭环，不一次堆满界面。

## Migration Plan

1. 输出只读迁移预览，列出源库、章节数、关联歧义与目标位置。
2. 创建一致性备份、验证可恢复性；在新库事务导入，记录源标识和内容校验。
3. 比较章节数、正文校验及设定内容，重复执行必须无重复记录；歧义交由作者选择。
4. 通过配置切换工作台入口，旧入口保留为兼容入口且写入走统一服务。
5. 回滚时停止任务和写入，保留新库及增量导出，切回旧入口和备份。不得删除新版本数据；切换后的新增稿件需按版本导出并校验后恢复，不能直接恢复旧快照造成丢稿。
